# 타임카드 수정 오류 디버그 질문지

## 목적
- 오류 A: `Could not find the table 'public.timecard_adjustments' in the schema cache`
- 오류 B: 저장 버튼 클릭 후 즉시 반영 안 되고 F5 후 반영됨
- 위 2개가 같은 원인인지, 다른 원인인지 분리해서 확인

---

## 0) 사전 고정 정보
- 화면: `타임카드` 페이지
- 저장 경로 1(서버 액션): `?/updateTimecard`
- 저장 경로 2(24시간 초과 강제저장): 클라이언트 `forceSaveOver24h()`
- 감사 로그 테이블: `public.timecard_adjustments`

---

## 1) 스키마/캐시 점검 (오류 A)

### Q1. 실제 DB에 테이블이 있나요?
Supabase SQL Editor에서 아래 쿼리 실행:

```sql
select table_schema, table_name
from information_schema.tables
where table_schema = 'public'
  and table_name = 'timecard_adjustments';
```

- [ ] 1행 조회됨
- [ ] 0행(테이블 없음)

### Q2. 컬럼 구조가 맞나요?
```sql
select column_name, data_type, is_nullable
from information_schema.columns
where table_schema = 'public'
  and table_name = 'timecard_adjustments'
order by ordinal_position;
```

- [ ] `timecard_id`, `employee_id`, `store_id`, `reason`, `updated_by` 포함
- [ ] 누락 컬럼 있음

### Q3. 마이그레이션이 적용됐나요?
파일: `supabase/migrations/20260421120000_add_timecard_adjustments_audit.sql`

- [ ] 운영/개발 DB 모두 반영됨
- [ ] 로컬 파일만 있고 실제 DB 반영 안 됨

### Q4. 프로젝트 연결이 같은가요?
- 브라우저 클라이언트가 보는 Supabase 프로젝트 ref
- 서버 액션(SSR)이 보는 Supabase 프로젝트 ref

- [ ] 둘 다 동일 ref
- [ ] 서로 다름 (키/URL 엇갈림)

### Q5. 캐시 문제 가능성 확인
- 테이블 생성 직후였다면 잠시 후 재시도
- Supabase 대시보드/세션 재로그인 후 재시도

- [ ] 잠시 후 정상
- [ ] 계속 동일 오류

## 2) 권한/RLS 점검 (오류 A 확장)

### Q6. 정책이 insert를 허용하나요?
현재 정책 핵심 조건:
- `store_id in (내가 owner인 매장)`
- `updated_by = auth.uid()`

체크:
- [ ] 저장 시점 `updated_by` = 현재 로그인 유저 id
- [ ] `store_id`가 owner 매장 id와 정확히 동일
- [ ] 위 두 조건 모두 만족

### Q7. 에러 메시지 형태가 바뀌나요?
- [ ] 계속 “table not found in schema cache”
- [ ] “RLS 거부”/“permission denied”로 변경

> 해석:  
> - 계속 table not found면 **스키마/연결 문제 우선**  
> - RLS 계열로 바뀌면 **테이블은 존재, 권한 문제로 이동**

## 3) 즉시 반영 지연 점검 (오류 B)

### Q8. 저장 응답 타입 확인
DevTools Network에서 저장 요청 응답 확인:

- [ ] `success`
- [ ] `failure`

### Q9. failure면 왜 반영이 안 되나요?
- 서버 액션 코드는 `failure`일 때 목록 재조회(`fetchTimecards`)를 하지 않음
- 즉, 감사로그 insert 실패면 화면 즉시 갱신이 안 보일 수 있음

- [ ] 이번 케이스는 failure였다
- [ ] success였는데도 반영이 지연된다

### Q10. success인데도 안 보이면 필터 범위 문제인가요?
현재 목록은 `clock_in` 기준 월 필터(`pickYear`, `pickMonth`)로 조회함.

- [ ] 수정 후 `clock_in`이 다른 월로 이동함
- [ ] 같은 월인데도 목록에 없음

### Q11. 재조회 함수 호출 여부
- 일반 저장 성공 시 `fetchTimecards()` 호출
- 24시간 초과 강제 저장도 `await fetchTimecards()` 호출

- [ ] 함수 호출됨
- [ ] 함수 호출 안 됨 (이벤트/분기 문제)

### Q12. 두 저장 경로 동작 차이
- [ ] 일반 저장만 문제
- [ ] 24시간 강제 저장만 문제
- [ ] 둘 다 동일 문제

## 5) 원인 분류표 (결론 작성용)

### A. 스키마/연결 이슈
- 조건:
  - `information_schema.tables`에서 테이블 미존재, 또는
  - 브라우저/서버가 서로 다른 Supabase 프로젝트를 보고 있음
- 결론:
  - 마이그레이션 적용/프로젝트 ref 정렬 먼저 처리

### B. 권한/RLS 이슈
- 조건:
  - 테이블은 존재
  - insert 시 RLS/permission 오류
- 결론:
  - `store_id`, `updated_by`, policy 조건 점검 및 보정

### C. UI 즉시반영 이슈(조회 조건/갱신 흐름)
- 조건:
  - 저장은 success인데 목록 미반영
  - 또는 월 필터 경계 이동으로 화면에서 사라짐
- 결론:
  - 필터 기준 확인, 저장 직후 조회/토스트/가시성 UX 보강

## 6) 이번 건의 1차 추정 (현재 코드 기준)
- `timecard_adjustments` insert 실패 시 `failure`로 처리되어 즉시 재조회 분기가 실행되지 않음
- 그래서 사용자는 “저장 눌렀는데 바로 안 바뀜”으로 체감 가능
- 먼저 **테이블 존재/연결 프로젝트 일치**를 확정하면, 반영 지연 이슈가 같이 줄어들 가능성이 큼
